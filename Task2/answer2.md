# ADR-001. Гибридная приоритизация подозрительных операций: слабые метки + контрольная выборка, on-premises / гибрид по звеньям

**Статус:** предварительное  
**Дата:** 2026-11-15  
**Инициатива:** №1 — автоматически выявлять подозрительные операции по счетам (транзит, обналичивание, дробление платежей под пороги)

## Контекст

Банк обрабатывает 20–25 млн операций в месяц. Пороговые правила и внешние сигналы помечают около 35 тыс. операций, служба финмониторинга из 25 человек успевает разобрать ~10 тыс. Очередь растёт; приоритет отдаётся крупным суммам, а не риску схемы. Подтверждённых случаев «схема» — единицы, и появляются они спустя месяцы. Отметка «эскалировано на расследование» (~400 в месяц) не равна подтверждённой схеме: значительная часть расследований заканчивается ничем.

Для обучения с учителем этого недостаточно. Нужен сервис, который **не выносит вердикт «схема / не схема»**, а **меняет порядок очереди** на ручную проверку и накапливает разметку из двух источников одновременно: из разобранной приоритетной очереди и из постоянной вероятностной контрольной выборки.

## Жёсткие ограничения (отсекают варианты до сравнения)

1. **Банковская тайна и персональные данные.** Сведения об операциях и счетах — банковская тайна; данные клиентов, представителей и поручителей — персональные данные. Передача на обработку сторонним IT-компаниям допускается только аккредитованным компаниям / банкам с универсальной лицензией под российским контролем, с уведомлением ЦБ, аудитом ФСТЭК/ФСБ и нахождением информационных систем исполнителя на территории РФ. Для пилота это означает: либо on-premises, либо выделенный контур аккредитованного провайдера. Публичный API зарубежного вендора отсекается.
2. **Процедура ПОД/ФТ не отменяется.** Любое решение встраивается в правила внутреннего контроля. Автоматическая блокировка без человека недопустима: решение о приостановке/отказе — юридически значимое действие, требующее установленной процедуры и фиксации.
3. **152-ФЗ, ст. 16.** Решения, порождающие юридические последствия для субъекта исключительно на основе автоматизированной обработки, допускаются только при согласии субъекта или прямом указании федерального закона; оператор обязан разъяснить порядок и рассмотреть возражение в 30 дней. В пилоте это снимается тем, что модель **только ранжирует очередь**, а решение принимает человек.
4. **Внешняя платформа «Знай своего клиента»** — вспомогательный сигнал, не замена оценки банка. Окончательную оценку и ответственность несёт банк.

## Сравнительные критерии

| Критерий | Вес | Пояснение |
|---|---:|---|
| Правовая допустимость | обязательная проверка всегда | Не проходит — вариант отсекается |
| Контроль границ данных | 0.30 | Возможность не выпускать сырые данные за контур банка |
| Скорость пилота | 0.25 | Время до первого работающего ранжирования |

## Рассмотренные варианты

| Вариант | За | Против | Почему отклонён / выбран |
|---|---|---|---|
| **A. Публичный API зарубежной LLM / облако** | Быстрый старт, сильная модель | Банковская тайна и ПДн уходят за контур; нет аккредитации по 115-ФЗ; юрисдикция | **Отклонён по жёсткому ограничению** |
| **B. Выделенный контур аккредитованного российского провайдера** | Быстрее, чем on-prem; данные в РФ; возможен пилот | Требует уведомления ЦБ, аудита, 60-дневного ожидания; не все провайдеры аккредитованы; зависимость от вендора | **Допустим для пилота**, но не для самых чувствительных звеньев |
| **C. Self-hosting в облаке (VPC)** | Эластичные GPU, логическая изоляция, быстрее on-prem | «Private» относится к tenancy, не к юрисдикции; нужно проверять физическое хранение и доступ персонала провайдера | **Возможен для пилота**, если облако в РФ и соответствует 115-ФЗ |
| **D. On-premises полностью** | Максимальный контроль: данные не покидают банк; подходит для core-banking-adjacent нагрузок | Высокий CAPEX, 6–12+ месяцев до продакшена, GPU и эксплуатация | **Целевое решение для скоринга и финального ранжирования** |
| **E. Гибрид по звеньям** | Тяжёлые/чувствительные звенья on-prem; лёгкие/менее чувствительные — в аккредитованном контуре | Сложнее эксплуатация и контроль границ | **Выбран как компромисс для пилота** |

## Решение

**Для пилота (0–6 месяцев): гибрид по звеньям.**

- **Признаки и скоринг** (табличные данные, производные признаки, текст назначения после обезличивания) — **on-premises** или **VPC в РФ** в зависимости от доступной инфраструктуры.
- **Модель ранжирования** — градиентный бустинг на табличных признаках + TF-IDF/эмбеддинги текста назначения. Без генеративных LLM на сырых данных на первом этапе.
- **Выход** — только **ранг/приоритет** для очереди финмониторинга, не вердикт. Человек разбирает, решение и фиксация — по действующей процедуре.
- **Разметка** — два потока одновременно:
  1. разобранная приоритетная очередь (слабые метки: эскалация, исход расследования);
  2. **постоянная вероятностная контрольная выборка** — случайная или стратифицированная по сегментам и суммам, размечаемая экспертами финмониторинга по гайдлайну. Это даёт несмещённую оценку непроверяемой части потока.
- **Без учителя / слабые метки:** на старте — ранжирование без учителя или обучение на слабых метках с честной оговоркой, что эскалация не равна схеме, а модель воспроизводит логику существующих правил. Через 3–6 месяцев накопления контрольной выборки — переход к обучению с учителем на объединённой разметке.

**Для целевого прода (6–18 месяцев): on-premises для скоринга и ранжирования; гибрид по звеньям допустим для нечувствительных вспомогательных задач.**

- Скоринговая модель и признаки — on-prem.
- Если используется LLM для работы с текстом назначения или объяснений — только self-hosted / on-prem LLM (например, vLLM на GPU) или аккредитованный российский контур.
- Человек в контуре сохраняется; автоматическая блокировка не вводится.

## Допущения

| Допущение | Источник | Критично для вывода |
|---|---|---|
| Контрольную выборку можно размечать силами финмониторинга без остановки текущего процесса | Оценка ёмкости службы (25 человек, 10 тыс. разборов/мес) | Да: без контрольной выборки нельзя получить несмещённую оценку |
| Согласованность разметчиков ≥ 0.6 по каппа Коэна достижима после калибровки | Практика разметки в AML | Да: иначе метки шумные и модель не обучится |
| On-prem GPU-мощности достаточно для скоринга на 20–25 млн операций/мес | Инфраструктурное допущение | Да: иначе пилот на VPC, прод — гибрид |
| Комплаенс и юристы подтвердят допустимость ранжирования без автоматической блокировки | Требуется подтверждающий | Да: иначе постановка меняется на «только аналитика для человека» |

## Риски и что с ними делаем

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Смещение отбора: модель учится на том, что уже отобрали правила | Высокая | Высокое | Контрольная выборка + стратификация; не использовать эскалацию как целевую метку |
| Утечка данных через вендора пилота | Средняя | Критическое | Только аккредитованный провайдер / on-prem; договор с требованиями 115-ФЗ; аудит |
| Разметчики расходятся | Средняя | Среднее | Гайдлайн, калибровка, измерение каппы, арбитраж |
| Модель воспроизводит правила и не находит нового | Высокая | Среднее | Отдельный контур unsupervised / anomaly detection; оценка на контрольной выборке |
| Регулятор не принимает автоматизированное ранжирование | Низкая | Высокое | Human-in-the-loop, объяснимость, sign-off комплаенса до пилота |

## План выхода от вендора

- **Пилот на аккредитованном контуре:** контракт с ограничением срока, экспорт признаков и модели в открытых форматах (ONNX / pickle + feature store schema). При смене условий — перенос на on-prem без переобучения с нуля.
- **On-prem:** вендор-независимый стек. Нет привязки к проприетарному SaaS.
- **Данные разметки** хранятся в банке; вендор получает только обезличенные признаки, если пилот в внешнем контуре.

## Триггеры пересмотра

1. Комплаенс/юристы не подтверждают допустимость ранжирования без автоматической блокировки — пересмотр постановки.
2. Согласованность разметчиков < 0.5 — пересмотр гайдлайна и/или переход на обучение без учителя.
3. On-prem GPU не обеспечивает нужную пропускную способность — пересмотр в сторону VPC / гибрида.
4. Изменение 115-ФЗ / 152-ФЗ в части автоматизированных решений — пересмотр границ автоматизации.
5. Появление достаточного объёма подтверждённых схем (> 500) — пересмотр в сторону supervised-классификатора.

## История

- **v0.1 2026-11-15** — предварительное решение: пилот — гибрид по звеньям (скоринг on-prem/VPC + контрольная выборка), прод — on-prem; модель только ранжирует, не выносит вердикт. Основание: дефицит подтверждённых меток, правовые ограничения 115-ФЗ и 152-ФЗ.

# Паспорт инициативы №1 — разделы 2–5

## Раздел 2. Постановка

| Поле | Содержание |
|---|---|
| Бизнес-действие | Изменение порядка очереди на ручную проверку: высокорисковые операции разбираются раньше; автоматическая блокировка не вводится. |
| Объект и единица решения | Операция по счёту (одна операция = один объект ранжирования). |
| Момент | Near-real-time / streaming для очереди; batch для пересчёта и анализа. |
| Операция | Ранжирование / аномалия / классификация (вспомогательно). |
| Модальность | Таблица + текст назначения платежа. |
| Выход модели | Оценка риска 0–1 и ранг; коды причин / топ-признаки. |
| Бизнес-выход | Приоритет в очереди финмониторинга; алерт для человека; **не** автоматическая блокировка. |
| Источник правильного ответа | (1) Формально подтверждённые случаи — главный эталон, появляются поздно и единицами. (2) Исход расследования — weak label, не равен схеме. (3) Эскалация — сигнал отбора, **не** целевая метка. (4) Контрольная выборка, размеченная экспертами по гайдлайну — источник несмещённой оценки. |
| Конвейер | Детерминированные правила и признаки → ML-скоринг/ранжирование → правила-ограничители → человеческий разбор → фиксация. |
| Альтернативные постановки | (а) только приоритизация существующих алертов; (б) поиск новых схем вне правил; (в) вердикт «схема/не схема» (отклонён из-за дефицита меток). Различающий вопрос бизнесу: «Что важнее — разгрузить очередь или находить пропущенное?» |

## Раздел 3. Оценка качества

| Поле | Содержание |
|---|---|
| Бизнес-метрика | Доля подтверждённых схем в верхушке очереди (precision@K); количество разобранных операций на одно подтверждение; снижение пропусков на контрольной выборке. |
| Положительный класс | Операция, которая по гайдлайну финмониторинга является схемой (транзит, обналичивание, дробление, фиктивная сделка). |
| Метрика под решение | **Precision@K** при K = пропускная способность службы (например, 10 тыс. разборов/мес). Именно она отвечает на вопрос «стало ли больше схем в том, что люди реально успевают разобрать». |
| Baseline | Текущая очередь: приоритет по сумме + пороговые правила. Сравнение по precision@K и по доле схем, найденных в контрольной выборке. |
| Проверочная выборка | Отложенная контрольная выборка, стратифицированная по сегментам и суммам; размечена экспертами, **не** отобрана моделью. Оценка на ней честная, потому что не воспроизводит смещение исторических правил. |
| Рабочая точка | K = 10 000 операций/мес (текущая пропускная способность); модель ранжирует, люди разбирают верхушку. |
| Показатели в этой точке | Ожидаемый прирост precision@K относительно baseline; целевой ориентир — +30–50% к доле подтверждённых схем в верхушке (уточняется на пилоте). Нагрузка на людей не растёт: K фиксирован. |
| Цена ошибок | Ложное срабатывание (лишний разбор) — стоимость ~12 минут рабочего времени; пропуск схемы — риск претензий надзора (два предписания за прошлый год, устранение месяцами) и репутационный ущерб. Асимметрия: пропуск дороже ложного срабатывания, но автоматическая блокировка недопустима. |
| Guardrails | Не должна расти доля необоснованных блокировок (сейчас ~600 приостановок/мес, 450 снимаются); не должно снижаться покрытие контрольной выборки; задержка ранжирования не выше согласованного SLA. |

## Раздел 4. Готовность данных

| Поле | Содержание |
|---|---|
| Решение | Ранжирование операций для ручной проверки; накопление разметки для будущего supervised-классификатора. |
| Объект и гранулярность | Операция по счёту; запись на уровне отдельной транзакции с признаками клиента, контрагента, канала, текста назначения. |
| Источник и владелец | Транзакционный журнал АБС, справочники тарифов/лимитов, внешние сигналы. Владелец — ИТ-блок и служба финмониторинга; доступ — через комплаенс. |
| Источник правильного ответа | **Дефицит точного эталона.** Подтверждённые схемы — единицы и с задержкой в месяцы. Поэтому: (1) слабые метки (эскалация, исход расследования) — только как сигнал, не как истина; (2) **постоянная вероятностная контрольная выборка**, размечаемая экспертами, — источник несмещённой оценки; (3) накопление разметки из двух потоков одновременно. |
| Доступность признаков в проде | Да: сумма, назначение, контрагент, ОКВЭД, канал, история — доступны в момент ранжирования. Текст назначения доступен. |
| Разметка | Эксперты финмониторинга по гайдлайну; измерение согласованности (каппа Коэна); калибровка и арбитраж. Контрольная выборка размечается независимо от очереди. |
| Смещение отбора | **Критично:** исторические проверки отбирались пороговыми правилами и внешними сигналами; непроверенная операция не равна чистой. Обучение только на эскалациях воспроизводит логику правил. Контрольная выборка компенсирует это. |
| Репрезентативность | Нужна стратификация по сегментам (ИП / юрлица), суммам, каналам, регионам. Редкие дорогие схемы должны попадать в выборку. |
| Объём | Общий поток — 20–25 млн операций/мес. Важный класс (схемы) — единицы подтверждённых; эскалации ~400/мес. Для обучения с учителем недостаточно; для ранжирования и накопления — достаточно при контрольной выборке. |
| Качество | Пропуски в назначении платежа (свободная форма), неоднородные справочники, возможные дубли. Требуется очистка и унификация. |
| Право использовать | Банковская тайна и ПДн. Для пилота — только on-prem или аккредитованный контур по 115-ФЗ (уведомление ЦБ, аудит, ИС в РФ). Вопросы допустимости — к комплаенсу, DPO и юристам; архитектор их не решает. |
| **Вердикт** | **Разрыв с планом закрытия:** размеченных данных для supervised-классификатора недостаточно. Сначала — программа сбора разметки (контрольная выборка + разбор очереди); сервис на старте — **ранжирование**, не вердикт. |

## Раздел 5. Карточка эксперимента

| Поле | Содержание |
|---|---|
| Где именно теряем | В верхушке очереди: приоритет по сумме пропускает схемы на малых и средних суммах; в непроверенной части потока доля схем неизвестна. |
| Гипотеза причины | Текущий приоритет не использует поведенческие и текстовые признаки; модель на слабых метках + контрольной выборке сможет поднять precision@K. |
| Конкурирующие объяснения | (а) Верхушка уже близка к потолку, и прирост невозможен; (б) контрольная выборка смещена из-за сезонности; (в) разметчики расходятся настолько, что сигнал нестабилен. |
| Рычаг | Признаки (поведенческие, текст назначения, граф связей) + постановка (ранжирование вместо вердикта) + порог/верхушка K. |
| Дешёвый различающий эксперимент | Разметить контрольную выборку (~2–3 тыс. операций) и сравнить precision@K модели и baseline на **одной и той же** выборке; одновременно измерить каппу. |
| Ожидаемый эффект | +30–50% к precision@K относительно baseline на стратифицированной контрольной выборке; без роста нагрузки на людей. |
| Стоимость проверки | 4–6 недель, 2–3 эксперта финмониторинга частично, 1 ML-инженер, инфраструктура on-prem/VPC. |

## Краткий итог по Заданию 2

- **Флагман (№1):** данных для supervised-классификатора недостаточно; выбран путь **ранжирования** на слабых метках + **контрольная выборка** с разметкой экспертов. Пилот — гибрид по звеньям, прод — on-prem. ADR фиксирует это с допущениями и триггерами пересмотра.
- **№2:** данных достаточно для пилота на ограниченном наборе полей; размещение — в контуре банка (on-prem / аккредитованный контур).
- **№14:** пилот возможен после проверки извлечения условий договора; расчёт — детерминированный, ML — только на извлечении/аномалиях.
- **Правовые вопросы** (115-ФЗ, 152-ФЗ, банковская тайна) адресованы комплаенсу и юристам, а не решены архитектором.
