## 2. Выходной контракт

### 2.1. Флагман — `ScoringResult`

```json
{
  "operation_id": "uuid",
  "client_id_hash": "sha256",
  "score": 0.0,
  "rank": 1234,
  "reason_codes": ["SPLIT_PAYMENTS", "TRANSIT_COUNTERPARTY"],
  "model_version": "v1.2.3",
  "feature_snapshot_id": "fs-2026-11-15-001",
  "fallback": false,
  "fallback_reason": null,
  "validation_status": "passed",
  "source_refs": {
    "abs_transaction_id": "...",
    "kyc_signal": null
  },
  "generated_at": "2026-11-15T10:00:00Z"
}
```

**Обязательные поля:** `operation_id`, `score`, `rank`, `model_version`, `validation_status`, `fallback`, `generated_at`, `feature_snapshot_id`.

**Детерминированные проверки до записи в очередь:**
- `score ∈ [0,1]`, `rank ≥ 0`, `operation_id` существует в АБС;
- `model_version` есть в реестре моделей;
- `feature_snapshot_id` существует и не старше SLA;
- `reason_codes` непусты при `score > threshold`;
- `validation_status == "passed"`.

**Поведение при отсутствии данных:** `fallback = true`, `fallback_reason = "missing_features"`, `rank` присваивается baseline-правилами (приоритет по сумме + пороговые правила). Кейс **не блокируется**, уходит в очередь с пометкой.

**Валидация до бизнес-действия:** Output Validator → Schema Validator → Rules & Guardrails. Только после этого Queue Writer пишет в очередь. Решение о блокировке/отказе — **только человек** по процедуре ПОД/ФТ.

### 2.2. №2 — `ExtractedDocument`

```json
{
  "document_id": "uuid",
  "doc_type": "account_statement",
  "fields": [{"name": "inn", "value": "...", "confidence": 0.97, "bbox": [x,y,w,h]}],
  "validation_status": "passed",
  "requires_review": false,
  "model_version": "v0.9.1",
  "source_ref": {"page": 1, "bbox": [x,y,w,h]}
}
```
Обязательные: `document_id`, `doc_type`, `fields`, `validation_status`, `model_version`. При `confidence < threshold` — `requires_review = true`.

### 2.3. №14 — `DiscrepancyResult`

```json
{
  "contract_id": "uuid",
  "extracted_conditions": {"rate": 0.019, "scheme": "monthly"},
  "discrepancy": {"expected": 19000, "actual": 21000, "diff": 2000, "clause_ref": "п. 3.2"},

  "model_version": "v0.4.0"
}
```
Обязательные: `contract_id`, `extracted_conditions`, `discrepancy`, `confidence`, `model_version`.

## 3. Фолбэк

### Флагман (скоринг)
| Наблюдаемый признак | Маршрут |
|---|---|
| Нет/устарели признаки | `fallback=true`, baseline-правила, пометка в очереди |
| Значение за границами обучения (OOD) | `fallback=true`, к человеку с пометкой |
| Клиент/сегмент без истории | `fallback=true`, к человеку |
| Score в зоне воздержания около порога | к человеку, приоритет по правилам |
| Расхождение score с сигналом правила | Conflict Checker → к человеку |
| Модель/Feature Service недоступны | baseline-правила, инцидент в Monitoring |
| Отказ внешнего сервиса / rate limit | baseline, инцидент |

### №2 (документы)
| Признак | Маршрут |
|---|---|
| Не прошла схема ответа | в Exception Queue |
| Нет подтверждающего источника (bbox/страница) | в Exception Queue |
| Документы противоречат друг другу | в Exception Queue |
| Запрос вне области применимости | в Exception Queue |
| Отказ OCR/модели | в Exception Queue + инцидент |

### №14 (договоры)
| Признак | Маршрут |
|---|---|
| Низкая confidence извлечения | к аудитору |
| Неизвестный формат договора | к аудитору |
| Расчёт не сходится с известными случаями | к аудитору |
| Отказ модели | к аудитору + инцидент |

## 4. Мониторинг

| Слой | Что отслеживаем | Триггер |
|---|---|---|
| **Вход** | Доля нарушений схемы, пропуски в назначении, дрейф распределения сумм/сегментов (PSI), задержка ingest | PSI > 0.2 → проверка; пропуски > 5% → инцидент |
| **Модель** | Распределение score, калибровка (reliability), дрейф (KS/PSI), доля фолбэка, распределение reason codes | Fallback rate > 10% → инцидент; drift > порога → переобучение |
| **Очередь человека** | Глубина, время разбора, согласие модели и человека, доля эскалаций | Согласие < 60% → ревью модели; рост глубины → capacity |
| **Бизнес-метрика** | precision@K, подтверждённые схемы на 1000 разборов, доля необоснованных блокировок (600→?), жалобы (120/мес), отток | precision@K падает > 10% за 2 недели → откат модели; рост жалоб → ревью порогов |

**Что запускает повторную проверку/откат:** падение precision@K, рост fallback rate, drift, падение согласия человека с моделью, инцидент безопасности на границе доверия.

## 5. Границы доверия: «граница → угроза → что делаем»

### №1 — вход недоверенного контента (текст назначения, поля операции, документы клиента)

| Угроза | Что делаем |
|---|---|
| Prompt injection в тексте назначения (если LLM) | В пилоте LLM не используется на сыром тексте; TF-IDF/эмбеддинги без генерации; строгий whitelist полей |
| Отравление данных через специально сформированное назначение | Валидация схемы, лимиты длины, кодировки, санитайзинг; аномалии текста — сигнал, не инструкция |
| Инъекция в поля операции (типы, переполнения) | Строгая схема, типы, диапазоны, отказ при нарушении |
| Вредоносный документ (для №2) | Антивирус, проверка MIME, sandbox-парсинг, лимит размера |

### №2 — выход из контура (агрегаты в аналитику)

| Угроза | Что делаем |
|---|---|
| Утечка банковской тайны / ПДн | Только агрегаты; k-anonymity; DLP на границе; аудит доступа |
| Ре-идентификация по агрегатам | Минимальный размер группы; запрет на редкие срезы |
| Несанкционированный доступ | Аутентификация, RBAC, журналирование |

### №3 — внешний API «Знай своего клиента»

| Угроза | Что делаем |
|---|---|
| Недоверенный ответ (подмена, spoofing) | mTLS, проверка подписи/сертификата, валидация схемы ответа |
| Недоступность / rate limit | Fallback на собственные данные, инцидент в Monitoring |
| Утечка данных во внешнюю систему | Передаём минимум; договор с требованиями 115-ФЗ; без сырых ПДн |
| Сигнал воспринимается как истина | Явно помечаем как вспомогательный; окончательная оценка — банк |

### Сквозные (не на диаграмме, чтобы не перегружать)

| Угроза | Что делаем |
|---|---|
| Подмена весов модели | Реестр моделей с checksums и подписью; загрузка только из реестра |
| Уязвимые зависимости | SBOM, pinned versions, скан уязвимостей в CI |
| Избыточные права сервисов | Least privilege, отдельные service accounts, secrets manager |
| Утечка через логи | Маскирование ПДн, запрет сырых данных в логах |
